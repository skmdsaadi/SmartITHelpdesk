# Synthetic ticket dataset — provenance and annotation policy

## Origin

`ticket_examples.json` contains 324 original, English, illustrative IT issue descriptions generated by the development assistant for this capstone. They were written for the project, not scraped or copied from another dataset. They contain no employee accounts, passwords, names, confidential tickets or customer records. Independent human annotation review has not yet taken place.

This is a bootstrap demonstration dataset, not production support evidence. There is no third-party dataset license or claimed organizational permission. A general repository reuse license has not been selected.

## Record format

Each record has `id`, `group`, `category`, `text`, `source` and `language`. Source is `project_authored_synthetic_v1`; language is `en`.

There are 54 examples per category: 18 issue-intent groups with three paraphrases each. `group` identifies the underlying issue, not a random row. All three paraphrases stay in the same partition. Exact normalized duplicate text and duplicate IDs are rejected. Intent grouping is manually authored and does not prove that every semantic overlap between groups has been eliminated.

| Category | Annotation rule |
| --- | --- |
| Access | Credentials, authentication, account lifecycle, roles and permissions, including VPN/mailbox login or authorization |
| Email | Mail transport, synchronization, inbox/search/calendar/message behavior after access is established |
| Network | Connectivity, routing, DNS, DHCP, bandwidth, wireless and VPN transport failures after authentication |
| Hardware | Physical computer/peripheral/power faults and hardware diagnostics, excluding printer-specific requests |
| Software | Application/OS installation, updates, runtime faults and licensing; explicit authorization problems belong to Access |
| Printer | Printer/scanner, consumables, print queues, printer drivers and print output; the printer-specific service takes precedence |

Mixed-issue requests are not comprehensively represented. The user must confirm the final category.

## Partitioning

For each category, intent group names are sorted by SHA-256 of `helpdesk-group-split-27` plus the group name. The first three groups are validation, the next three test, and the remaining twelve training. This yields 216/54/54 examples across 72/18/18 groups. No group crosses partitions.

Only the training partition fits TF-IDF and Logistic Regression. Validation chooses the abstention threshold. The test split is reserved for reporting. See `docs/evaluation/split_manifest.json` for the exact membership.

`out_of_scope.json` contains 12 validation and 12 test negative controls, also generated for this project. They include unrelated administrative/personal requests and vague issue descriptions. They are never positive-class training examples. The test negative controls include one false acceptance; the report retains that result.

The model ID hashes canonical parsed JSON, so Windows CRLF conversion does not change the dataset identity. Changes to data, grouping, policy or algorithms must be versioned and accompanied by a fresh evaluation plan.

## Before real deployment

Obtain explicit permission to use an anonymized support-ticket sample. Remove credentials and identifiers before export. Have IT reviewers label ambiguous cases under the taxonomy above. Keep duplicates, follow-ups and related incidents in one group; reserve a later or independently collected test sample. Compare macro-F1, per-class recall, abstention coverage and false acceptance. Evaluate Bangla and Banglish separately before claiming support. Stored application tickets and administrator corrections are not automatically included in model training.
